# Tooling and acceptance

## Derived model

Tools may materialize document identity, sections, semantic statements, typed
relationships, incoming edges, evidence, manifest facets, blockers, assets,
and full-text fields. Derived storage is deterministic, disposable, and never
an independent editing authority.

Exact IDs and paths outrank broad lexical matches. Implementation ranking
weights are not canonical specification data.

## Responsibilities

- Shared format and semantics own the v3 contract.
- Templates provide minimal valid roots and nodes.
- Checker owns deterministic integrity findings.
- Extract owns deterministic structured retrieval.
- Map compares repository evidence with accepted intent, retains only
  architecture-significant gaps, divergences, uncertainty, and necessary
  navigation observations, and records bounded inspection coverage without
  manufacturing intent or claiming conformance.
- Evolve creates and evolves accepted specification.
- Doctor diagnoses and repairs Spine health within authorization.
- Verify assesses implementation or reconstruction conformance.

Runtime skills remain framework-neutral. Feature planning, delivery state, and
implementation-specific testing remain downstream.

## Acceptance

### Human readability

Without special tooling, a reader can navigate from `README.md`, understand
ownership and boundaries, distinguish intent from evidence, and find
uncertainty and divergence. `specspine.json` makes completeness, blockers, and
assets inspectable without prose interpretation.

### Determinism

The same root produces the same graph, area status, registered asset set, and
retrieval result. Deleting derived storage loses no canonical information.

### Authority

Agents never promote `OBS` or `INF` into intent, silently resolve an `OQ`,
invent a missing contract, or treat current code as automatic authority over an
accepted claim.

### Retrieval

Evaluation targets 100% canonical-owner and applicable normative-claim recall,
100% registered-asset recall, near-100% required-neighbor recall, and explicit
no-match, truncation, invalidity, incomplete facets, and blockers.

### Reconstruction

For every `ready` benchmark slice:

- all applicable claims and assets are retrieved;
- no blocking choice is hidden;
- a blind implementation can build and pass an independent conformance suite;
- every policy invented by the implementing agent is recorded as a
  specification gap.

Code similarity is not a goal. Success is contract or architecture equivalence
according to `implementation_freedom`.

## Delivery boundary

SpecSpine does not require a graph database, YAML frontmatter, embeddings,
generated narratives, runtime telemetry ingestion, feature planning, task
management, release tracking, or implementation source.

The final invariant is:

> SpecSpine stores durable accepted system intent once in readable Markdown,
> records completeness and exact assets once in `specspine.json`, and exposes
> enough deterministic closure and verification for independent
> reconstruction without policy invention.
